### 2.2 정적 검사 / 코딩 규칙 (MISRA 성향 자체 점검 — 공식 MISRA 도구 아님)

## 3. Task10ms / Task10us 설계자 관점

### 3.1 주기 실행의 결정성 — 양호

- `X_Main` 1회 = 입력 래치 → (tm 카운터 증가) → 활성 경로의 Guard 검사 → 전이 최대 1개 → 출력 기록. **생성 코드에 루프가 없습니다**(사용자 액션 코드 제외).
- 조건 없는 전이가 이어져 있어도(A→B→C) 한 호출에 한 칸씩 갑니다. Rhapsody의 null transition처럼 한 호출 안에서 끝없이 도는 일이 없습니다.
- 같은 상태에서 나가는 전이가 여러 개면 **그린 순서(만든 순서)대로 첫 번째 참인 Guard**가 이깁니다. 우선순위가 눈에 보이지 않는 것은 위험 요소입니다. → 4.3 권고.

  **→ 반영 완료 (2026-10-17):** 라벨에 ①②… 번호가 붙고, 전이 카드에서 ▲▼로 순서를 바꿉니다(프로젝트에 `prio`로 저장, 생성 코드의 `if / else if` 순서가 그대로 바뀜). 조건 없는 전이는 항상 마지막이고, 그런 전이가 2개 이상이면 생성기 경고와 Problems 경고가 나옵니다. `test_priority.py`가 실제 실행으로 확인합니다(그린 순서 / prio 역전 / 조건 없는 전이는 마지막 / 경고).

### 3.2 실행 시간 (WCET) — PC 상대값만, 타깃 측정 필요

`/O1` x86 코드 크기, 인스턴스 RAM(`sizeof`, x64), `X_Main` 1회 PC 시간(x64 `/O2`, 입력 기본값 = 대부분 전이 없음 → **하한값**):

| 모듈 | .text (byte) | RAM (byte) | ns / X_Main (PC) |
|---|---:|---:|---:|
| SoftPwm (10 us) | 372 | 6 | 1.7 |
| Lamp | 467 | 12 | 1.7 |
| Button (debounce) | 443 | 20 | 2.2 |
| Led | 447 | 16 | 2.3 |
| Controller / Motor | 460 / 687 | 12 / 16 | 2.0 / 2.3 |
| Signal | 510 | 24 | 2.5 |
| Machine | 583 | 24 | 2.0 |
| Modem | 654 | 28 | 3.0 |
| Washer | 1046 | 24 | 3.5 |
| TrafficLight (AND + 히스토리) | 1489 | 48 | 4.9 |

- 10 us Task 예산: 72 MHz Cortex-M3 ≈ 720 사이클, 170 MHz Cortex-M4 ≈ 1700 사이클. 위 모듈들의 경로 길이(Guard 몇 개 + switch 2~3단)는 **수십~백여 사이클 수준으로 추정**합니다. 다만 추정일 뿐이므로 타깃에서 아래처럼 재야 합니다.
  ```c
  uint32_t t0 = DWT->CYCCNT;  io_pin = SoftPwm_Main(&pwm, en, duty);  wcet = max(wcet, DWT->CYCCNT - t0);
  ```
  최악 경로는 **가장 깊은 상태에서, exit/entry 액션이 가장 긴 전이가 일어나는 호출**입니다. 시뮬레이터에서 그 전이를 Step으로 일으켜 그 호출을 재세요.
- **런타임 tm(변수)**: `tm(greenTime)`처럼 상수가 아니면 `X_TM_TICKS`가 **매 호출 나눗셈**을 합니다(10 ms 주기: `(ms + 9) / 10`). 하드웨어 나눗셈이 없는 Cortex-M0에서는 수십 사이클입니다. 상수 tm은 컴파일 시간에 계산되어 비용이 없습니다. → 4.2 권고.

  **→ 반영 완료 (2026-10-17):** 상수가 아닌 tm은 상태 진입 때 한 번 `me-><상태>_limit = (uint32_t)(식) / 10u` 처럼 계산하고, 매 호출은 비교만 합니다(TrafficLight RAM 48 → 52 byte). 의미도 Rhapsody와 같아졌습니다: 머무는 동안 값을 바꿔도 지금 타이머는 그대로, 다음 진입부터 적용. 교차로 신호등 시나리오(9 checks 추가)와 `test_priority.py`로 확인했습니다.

### 3.3 tm() 해상도 · 오버플로

**변경 (2026-10-17):** 시스템 Task 주기를 프로젝트를 만들 때 먼저 고르고, `tm(상수)`는 생성할 때 호출 횟수(숫자)로 바뀌어 코드에 그대로 들어갑니다. 매크로(`X_TM_TICKS`, `X_TASK_PERIOD_US`)는 없앴습니다. 주기의 배수가 아닌 상수와 `tm(0)`은 이제 **생성 오류**입니다(전에는 올림 + 경고).

| 주기 | 해상도 | 상수 `tm(ms)` | `tm(식)` (진입 때 한 번) | 상태 카운터 포화 시점 |
|---|---|---|---|---|
| 100 ms | 100 ms | `tm(500)` → `5u` | `(uint32_t)(식) / 100u` | 4.29e9 회 ≈ 13.6년 |
| 10 ms | 10 ms | `tm(500)` → `50u` | `(uint32_t)(식) / 10u` | ≈ 497일 |
| 1 ms | 1 ms | `tm(500)` → `500u` | `(uint32_t)(식)` | ≈ 49.7일 |
| 10 us | 10 us | `tm(5)` → `500u` | `(uint32_t)(식) * 100u` (식 ≤ 42,949,672 ms) | ≈ 11.9시간 |
| 300 us | 300 us | `tm(3)` → `10u` | `((uint32_t)(식) * 1000u) / 300u` | ≈ 14.9일 |

- 시스템 주기와 다른 클래스(예: 10 ms 시스템에 100 ms 클래스)를 섞을 때, 시뮬레이터가 느린 클래스를 자기 주기의 **시작**에 부르던 결함을 고쳤습니다(전: 100 ms 클래스의 `tm(500)`이 410 ms에 일어남 → 지금: 500 ms). `test_priority.py`가 확인합니다.
- 카운터는 포화되므로 오래 머물러도 0으로 돌아가 다시 일어나는 일은 없습니다.
- tm은 **호출 횟수**입니다. Task가 밀리거나 건너뛰면 그만큼 늦어집니다(실제 시간을 보지 않음). 주기 오버런이 있는 시스템이면 4.4 참고.

### 3.4 ISR / Task 경계, 펄스 유실

- 입력은 값으로 넘어가고 호출 시작에 래치되므로, **한 호출 안에서는 값이 바뀌지 않습니다**(Guard끼리 서로 다른 값을 보는 일 없음).
- 펄스성 입력(버튼 엣지, 수신 완료)을 ISR에서 만들면 **다음 `X_Main`까지 유지해야** 합니다. ISR에서 플래그를 세우고, Task에서 읽은 뒤 지우는 방식이 필요합니다.
  ```c
  volatile bool rxDone;                              /* ISR: rxDone = true; */
  void Task_10ms(void) {
      bool ev; __disable_irq(); ev = rxDone; rxDone = false; __enable_irq();
      Modem_Main(&modem, ev, …);
  }
  ```
- Event 입력은 큐에 쌓이지 않습니다. 그 호출에 그 입력을 읽는 전이가 활성 상태에 없으면 **버려집니다**(Rhapsody가 처리하지 않는 이벤트를 버리는 것과 같음). 한 주기에 여러 번 일어날 수 있는 사건은 카운터 입력(`uint8_t pulses`)으로 넘기세요.
- 같은 인스턴스의 `X_Main`을 ISR과 Task 양쪽에서 부르면 안 됩니다(인스턴스 단위로 재진입 불가). 인스턴스가 다르면 문제없습니다(모듈에 전역 상태 없음).

### 3.5 다중 인스턴스 · RAM/ROM — 양호

- 인스턴스 RAM = 입력 + 출력 + 변수 + 상태 변수(복합 상태당 `uint8_t`) + tm 상태당 `uint32_t`. 예제는 6~48 byte입니다.
- 코드는 클래스당 한 벌이고, 인스턴스를 늘려도 ROM은 늘지 않습니다.
- 입력은 호출자 변수와 구조체에 **두 번** 저장됩니다(래치 비용: 입력 하나당 byte 몇 개).

### 3.6 인자가 많을 때의 호출 비용

ARM AAPCS에서 레지스터로 넘어가는 인자는 4개(`me` 포함)까지입니다. 입력이 3개를 넘거나 `o_` 포인터가 많으면 스택으로 넘어가 호출마다 저장·적재가 늘어납니다(10 us Task에서는 무시하기 어렵습니다).
예: Motor = `me` + 입력 3 + 출력 2 = 6개.

**→ 반영 완료 (2026-10-17):** 클래스마다 `X_Main 인자: 구조체`를 고르면 `X_Main(me, const X_In* const in, X_Out* const out)` (인자 최대 3개)가 됩니다. 파라미터 방식에서 인자가 4개를 넘으면 Problems에 경고가 나옵니다. 예제 중 인자가 4개를 넘던 세탁기·교차로 신호등·모터·모뎀을 구조체 방식으로 바꿨고, 10개 예제가 모두 `/W4 /WX`·`/analyze` 경고 없이 빌드되며 시나리오 94개가 통과합니다. 래치 비용은 같습니다(입력은 여전히 `me`에 복사). 대신 호출자 쪽 `X_In` / `X_Out` 변수가 RAM에 하나씩 더 생깁니다.

### 3.7 시작 직후의 출력

`X_Init`의 진입 액션이 `me->led = false`를 해도, 출력은 `X_Main`이 끝날 때만 밖으로 나갑니다. 첫 `X_Main` 전까지 main.c의 `io_` 출력은 변수 초깃값입니다. 하드웨어 초기 상태가 중요하면 `X_Init` 뒤에 `itsLed.led`를 직접 읽어 핀을 맞추거나, 초깃값을 같게 주세요.

### 3.8 액션 코드의 printf / float

예제의 `printf`는 시뮬레이터용입니다. MCU에서는 지우거나 매크로로 바꾸세요. FPU가 없는 MCU에서 `float` 입력·출력은 소프트웨어 연산이 됩니다(엣지 케이스로 빌드만 확인).
